# 10.1 — A checkpoint survives only as long as its storage

[Mission](../../MISSION.md). **Objective:** inspect a paused thread in a second process without changing its owner.

## Prerequisites and recall
Module 09 and Module 05 identity isolation. What does thread ID identify? Does a model retain application state? Which channel tells the draft's origin? Attempt answers before consulting the workflow source.

## Source and compatibility
[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) and [SQLite checkpointer](https://reference.langchain.com/python/langgraph/checkpoints/), checked 2026-10-12. Installed baseline: Python 3.14.0, LangGraph 1.2.14, langgraph-checkpoint-sqlite 3.1.1; [lockfile](../../uv.lock), [exercised evidence](../../docs/VERIFICATION.md). SQLite is a local teaching store, not a distributed deployment recommendation. POSIX file locking requires macOS/Linux.

## Mental model and flow
A thread groups successive checkpoints. `SqliteSaver` persists graph snapshots and pending writes to disk. Closing a Python process discards Python objects but not committed database rows. A thread ID locates state; it does not authenticate anyone.

`SupportWorkflow` binds each thread to immutable metadata in the action database: owner, stable action ID, original input and later human decision. The checkpoint database separately records its bound action-database path, preventing an accidental restart against a new empty sink. Treat both files and the lock as application-private data; local filesystem access is outside the caller boundary.

| File | Responsibility |
|---|---|
| support.sqlite | LangGraph snapshots plus sink binding |
| actions.sqlite | owner bindings, human decisions, committed actions |
| support.sqlite.lock | serialize local processes using this workflow |

## Guided completion and failure investigation
Predict what happens if bob starts alice's thread ID after restart. It must fail before revealing state or replacing owner metadata. Predict what happens if alice supplies a different draft on a repeated start: the original thread is inspected, not overwritten. If state appears missing, first compare both database paths, thread ID and working environment; do not start another thread and call it a successful resume.
