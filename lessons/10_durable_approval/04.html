10.4 — State history and business records answer different questions

In plain words: Graph snapshots, thread ownership and action records answer different questions. Use all three to see where a workflow is stuck and whether its effect happened.

Mission. Objective: diagnose a persisted workflow using snapshots, immutable metadata and action rows without confusing their responsibilities.

Prerequisites and recall

The first three lessons. Which file owns thread identity? Which contains replayable graph history? Can a terminal graph snapshot alone prove that no earlier effect occurred? Answer before examining the tables.

Primary sources and versions

Checkpoint history and SQLite transactions, checked 2026-10-12. Installed baseline: Python 3.14.0, LangGraph 1.2.14, langgraph-checkpoint-sqlite 3.1.1; lockfile, exercised evidence. Synthetic databases still deserve private storage and careful reset.

Mental model

A checkpoint answers: what state and next tasks did this graph have? An action record answers: what owned local effect committed? Thread metadata answers: who may inspect/resume, and which human decision was bound? No single layer replaces the others.

inspect(user_id, thread_id) checks metadata first, then returns serializable state, status, pending review and owned action rows. actions(user_id) filters actual records by owner. These IDs are trusted application arguments, not proof of login; the later HTTP service must authenticate before calling the API.

Worked diagnosis table

Run separate inspect and actions commands from the README, then explain:

Observation First diagnostic
pending plus zero rows expected approval boundary
rejected plus zero rows expected cancellation
recorded plus one row successful local effect
changed owner can inspect authorization defect, not prompt issue
restart opens another sink configuration mismatch; bound path must reject it

The implementation serializes workflow operations with a POSIX file lock and gives each context its own SQLite connections. This boring local constraint avoids concurrent graph resumes racing for one thread. It limits throughput and does not make SQLite a distributed service. The sink transaction commits inside the record node so a later checkpoint crash can safely replay it.

Guided completion and independent exercise

Inspect snapshot.next and task interrupts when explaining pending review. Do not expose the raw graph or historical checkpoint selection as an untrusted API; replay is a trusted operator/test activity. In the exercise, intentionally choose the wrong sink path and predict the binding failure before opening it.

Failure and exit checks

If a provider call fails before review, the bound owner remains unchanged; decision retry may recover pending graph execution before applying a human decision. A repeated start never replaces original input. Demonstrate persisted inspection, owner denial and correct edited action text. Delete only your dedicated demonstration databases after all processes exit; do not delete shared course state. Revisit storage privacy and rollback in Module 14. Solutions.
