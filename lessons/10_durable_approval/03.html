10.3 — Replay-safe effects need a stable identity and atomic sink

Mission. Objective: demonstrate one committed local action despite repeated approval and actual record-node replay.

Prerequisites and recall

Interrupt/resume. Why can code run again after restart? Does a checkpointer make external email exactly once? Which values must stay stable across a replay? Answer first; do not infer guarantees from a successful single run.

Source and version note

Durable execution and interrupt rules, checked 2026-10-12. Installed baseline: Python 3.14.0, LangGraph 1.2.14, langgraph-checkpoint-sqlite 3.1.1; lockfile, exercised evidence. The effect is an actual local SQLite record, not email, payment or a mock network response.

Mental model and failure window

A process can die after an effect commits but before the next checkpoint records completion. On restart, a pending node can repeat. The remedy here is not to prohibit replay: it is to make the local operation idempotent.

Thread creation generates one action ID and persists it before graph execution. Record inserts using a unique action ID and unique thread ID, inside a SQLite transaction. It then validates any existing row's owner, thread and text. Replaying an identical action reuses the committed row. An identity collision with different content fails instead of overwriting history.

Boundary Durable fact
start immutable owner and action ID
human decision approved/rejected/edited decision
record transaction one owned action row
next checkpoint graph completion

SQLite uniqueness and committed atomic insertion cover the sink/checkpoint crash window: a committed row remains singular even if the graph repeats record. This is an exactly-once local-record claim under intact private databases and cooperating local workflow callers. It is not a general distributed exactly-once guarantee. External effects would require their own idempotency contract or transactional outbox plus delivery semantics.

Worked example and guided investigation

Repeat the approve command in the README. Count rows, not printed success messages. Regression coverage also selects a real saved checkpoint whose next node is record and reexecutes the actual graph node. Parent verification runs it; this lesson does not fabricate an observed result.

Predict what happens if the action ID is generated inside record instead. Every replay could produce another identity; uniqueness would no longer represent the same business action. Explain this failure before modifying an exercise copy.
