# 10.2 — Interrupt before acting, then resume with a human decision

**In plain words:** `interrupt` pauses the graph and waits for a human to approve, reject or edit. When it resumes, the review step reruns from its start, so nothing with side effects may come before it.

[Mission](../../MISSION.md). **Objective:** approve, reject and edit a proposed action using the same durable graph thread.

## Prerequisites and recall
[Checkpoints](01.md), graph conditional edges, and grounded-answer limitations. Where does the side effect belong relative to review? Is human-authored fixture text a model answer? What identifies the resumed checkpoint? Attempt before reading the worked path.

## Sources and versions
[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), checked 2026-10-12. Installed baseline: Python 3.14.0, LangGraph 1.2.14, langgraph-checkpoint-sqlite 3.1.1; [lockfile](../../uv.lock), [exercised evidence](../../docs/VERIFICATION.md). Uses stable `interrupt(payload)` and `Command(resume=...)`, not a preview response-schema API. Human drafts need no model; real drafting requires provider consent.

## Mental model
`interrupt` suspends execution and surfaces JSON-serializable review information. A persistent checkpointer records the place to resume. The review node restarts from its beginning on resume; the supplied response becomes the interrupt's return value. Therefore pre-interrupt code must be safe to repeat, and no action should occur before review.

The support graph is draft → review → either END or record. Draft origin is explicit: a supplied `draft=` means a human-authored exercise; omitted draft requires `live=True` and calls actual `rag.answer`. The provider may abstain; humans still review the exact proposal rather than assuming schema validity proves policy correctness.

## Worked example
Start a human draft with the [CLI](../../labs/10_durable_approval/main.py). Inspect `pending_review`: it contains draft, origin, source IDs and allowed decisions. Resume with `--decision reject`; actions must remain empty. A fresh approve thread produces one local record. A third thread with `--decision edit --edited-draft 'Corrected reviewed text'` records the edited text rather than the initial proposal.

`decide` validates input, checks owner metadata, persists the immutable decision, then invokes the graph with `Command(resume=...)`. The review node checks that resume data matches that persisted decision. The record node checks again. Invalid edits fail before decision persistence; conflicting later decisions cannot silently change approval.

## Guided completion and diagnosis
Predict the effect of a blank edit and of bob resuming alice's thread. Run both only against synthetic local state. If an action appears while pending, inspect node placement; a polite approval prompt cannot repair an early side effect. If an edit records old text, inspect the review update and sink content, not merely the displayed review payload.
