# 05.2 — Store one preference explicitly across threads

## Objective and prerequisites

Advance the [mission](../../MISSION.md) by storing a synthetic, consented preference separately from conversation history. Prerequisite: [checkpoint state](01.md). Warm-up: which key scopes a conversation? Must every message become a long-term memory? Attempt before the exit corrections.

## Mental model: scope and durability are separate

The lab's checkpointer stores **thread state**. Its `InMemoryStore` stores **user-scoped documents across threads**. Both are in memory, so neither survives process exit. Calling the latter “long-term memory” describes the cross-conversation access pattern, not proof of durable storage.

| Object | Address | Content |
|---|---|---|
| Checkpointer | `thread_id` | Message history and selected-context snapshots |
| Preference store | `("preferences", user_id)`, key `response_style` | Exactly `{"style": "short"}` or `{"style": "detailed"}` |
| Invocation context | `SessionContext(user_id)` | Caller-selected identity for this invocation |

We retain one explicit response-style preference, not arbitrary user text, inferred traits, payment information or a shopping budget. `save_preference` requires consent and checks its allowed values. It is application-controlled, not a model-exposed write tool. Thus the agent cannot promote any sentence into permanent memory merely by choosing a tool.

## Worked store operation

```python
# See executable helpers in labs/05_memory_context/main.py.
store.put(("preferences", "alice"), "response_style", {"style": "short"})
item = store.get(("preferences", "alice"), "response_style")
assert item.value == {"style": "short"}
assert store.get(("preferences", "bob"), "response_style") is None
```

The actual lab uses validated helper calls rather than trusting arbitrary namespaces. Alice's new thread can access her preference but not her previous thread's messages. Bob receives an empty preference selection. In `--live`, `@dynamic_prompt` reads the user's exact namespace and emits the system context actually supplied. This is a narrow personalization hook, not a substitute for authentication.

## Complete, vary, diagnose

Guided completion: fill in the namespace's user component using trusted invocation context, not a user ID suggested in model text. Independent variation: persist Bob's distinct `detailed` preference with explicit consent and compare two new threads. Follow the [exercise](../../exercises/05_memory_context.md).

Failure investigation: delete Alice's store entry. The next lookup is empty, but an earlier checkpoint still contains the preference selected then. Deleting a store document does not erase all historical copies, traces or provider logs. The lab exposes this limitation instead of reporting fictional complete erasure.
