05.4 — Enforce identity separation and minimize retained data

Objective and prerequisites

Advance the mission by demonstrating a rejected cross-user thread access and identifying retained copies of a preference. Prerequisites: store scope and context selection. Warm-up: does asking the model not to leak history enforce isolation? Is a namespace string proof of authenticated identity? Attempt before the exit corrections.

Sources/version: Runtime context, long-term memory, and persistence, consulted 2026-10-12. Verification records Python 3.14 isolation checks, exact versions, and actual separate-user/thread model traces. Live runs transmit synthetic messages only with provider consent/charges; they do not certify production identity security.

Mental model: identify before loading

A thread_id is a storage lookup key. LangGraph does not infer that a thread called alice-shopping belongs to authenticated Alice. The application must bind identity and thread before loading checkpoint state, then pass immutable per-run context to store-selection code.

The lab's Sessions object accepts only the two synthetic users, validates a bounded thread identifier and records ownership in a process-local dictionary. A second user's attempt to reuse an owned identifier raises PermissionError before any graph invocation or checkpoint inspection. Store lookups use the exact ("preferences", user_id) namespace; broad cross-user searches are unnecessary.

trusted synthetic caller → ownership check → thread config
                         → user context → scoped store lookup
                         → model context

This is a teaching boundary, not production authentication. A caller who directly accesses the underlying graph can bypass the wrapper. The owner dictionary does not survive process exit and is not designed for concurrent service requests. Module 14 introduces authenticated requests and durable ownership; do not deploy this lab as a service.

Worked minimization and isolation

The lab records Alice's short-style preference, two Alice messages and one separate Bob message. Bob's selected preference is empty. Alice's second thread has her stored style but only its own message. The attempted Bob access to alice-shopping is rejected.

Only style is selected for model personalization. The application does not retain raw preference utterances as store documents or infer sensitive characteristics. Nevertheless, conversation checkpoints include human input, and the offline graph intentionally records a selected preference snapshot. Deleting the store entry leaves that historical snapshot. The live provider and optional trace services may retain additional copies according to their policies.

Complete, vary, diagnose

Guided completion: identify the earliest safe rejection point for a mismatched owner; place it before get_state, not merely before the final response. Independent variation: save different preferences for Alice and Bob, then test new threads and a reused thread ID in the exercise.

Failure investigation: remove identity from a copied store namespace and predict a collision. Use synthetic values only. Diagnose actual shared storage separately from a model guessing an absent fact; both are failures, but their repairs differ. Trimming messages cannot repair a wrongly scoped store read.

Exit and delayed review

Show no cross-user state, explicit rejection and a retained-copy inventory. Explain why this is not comprehensive erasure or authenticated production isolation. Corrections: prompts cannot enforce storage permissions; namespaces only organize data. Review in Modules 11 and 14 with fresh identities. Reference: troubleshooting. Focused follow-up: which persistent ownership check must exist before allowing an authenticated request to inspect a resumed thread?
