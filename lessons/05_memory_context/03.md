# 05.3 — Select, trim and summarize context visibly

**In plain words:** You can send the full history, only the recent part, or a summary. Each choice drops something, and summaries can be wrong, so you compare what each strategy kept and lost.

## Objective and prerequisites

Serve the [mission](../../MISSION.md) by comparing what information three context strategies retain and discard. Prerequisites: [thread history](01.md), [explicit preference store](02.md) and tool-message pairing. Warm-up: does dropping messages from a request delete checkpoints? Can a summary preserve every detail? Attempt before reading the corrections.

**Sources/version:** [Short-term memory strategies](https://docs.langchain.com/oss/python/langchain/short-term-memory) and [message trimming API](https://reference.langchain.com/python/langchain-core/messages/utils/trim_messages), consulted 2026-10-12. Python >=3.14 target; exact dependency versions are in the lockfile. Offline trimming is local. A generated summary and comparison agents require credentials, consent and several potentially paid model calls.

## Mental model and tradeoffs

Context engineering is selecting the information supplied now. Storage policy decides what remains available later. These can differ: the lab trims a **copy** for a fresh invocation and leaves the original checkpoint untouched.

| Strategy | Retains | Important loss or cost |
|---|---|---|
| Full history | Original messages and tool evidence | More tokens, stale facts, unrelated content |
| Recent trim | Complete recent messages within an approximate budget | Earlier budget/preferences can disappear |
| Summary + latest question | Compressed account of earlier interactions | Omitted details, inaccurate compression, extra model call |

The helper uses `trim_messages` with a last-message strategy, `start_on="human"`, and `end_on=("human", "tool")`. Complete boundaries matter: an assistant tool call without its correlated result is not valid conversation structure. `count_tokens_approximately` is a local estimate, not the provider's exact tokenizer or a guaranteed fit for every model. The latest question must fit by itself.

## Worked comparison

Run the [lab](../../labs/05_memory_context/README.md). Its deterministic path trims three actual human inputs: an early preference, a long unrelated discussion and a recent quote request. It prints full, trimmed and **human-authored summarized** contexts. That last text is expressly not a generated model response.

The live path obtains a real summary of actual Alice checkpoint messages through `get_model().invoke`. It then runs three fresh real catalog agents on full, trimmed and summarized versions of the same follow-up. Their exact selected input messages are emitted before invocation. Fresh agents prevent hidden old checkpoint state from invalidating the comparison. Current prices/stock must still come from new tool results, not a stale summary.

## Complete, vary, diagnose

Guided completion: list every fact in the original history, then mark which survives trimming and which the summary preserves. Supply a missing “discarded” annotation before seeing model answers. Independent variation: move the budget into the oldest message and lower the trim budget; use the [exercise](../../exercises/05_memory_context.md).

Predict a failure when a summary omits “cents” or changes 3000 to 300. Inspect summary content before blaming quote arithmetic. A valid schema cannot restore discarded meaning. Treat generated summaries as fallible data, not instructions or authorization. Comparing one run teaches mechanisms; it is not a statistically meaningful quality claim.
