05.1 — Conversation history is application state

Objective and prerequisites

Support the mission by identifying exactly which earlier messages reach a later model call. Prerequisite: Module 04 tools and trace inspection. Warm-up: does returning a response update model weights? Does a thread_id identify an authenticated user? Attempt first; corrections appear below.

Sources/version: Short-term memory and LangGraph persistence, consulted 2026-10-12. Verification records Python 3.14/locked versions, local state checks, and actual gateway-mediated follow-up/context calls. These examples are not a general recall-quality score. Live use requires compatible private access, consent, and budget.

Mental model and flow

A chat model sees the current request's messages and instructions. It does not acquire a personal database by changing its weights during our ordinary invocation. The application maintains history, chooses a thread, retrieves checkpoint state and includes that context in subsequent steps.

new human message + thread configuration
  → load checkpoint for that thread
  → append with message reducer
  → model/tools steps
  → save updated state

Without a checkpointer, creating another invocation does not automatically retain earlier messages. With InMemorySaver, the compiled graph can retrieve earlier state while the saver object exists. Rebuilding a graph against that same object can retain state; starting a new process with a new saver cannot. “Short-term” describes scope, not necessarily storage medium: a database-backed short-term checkpointer can persist across restarts.

Worked example

The memory lab creates InMemorySaver and runs a real StateGraph in --check. Its node selects a stored preference; it produces no assistant answer. Actual HumanMessage inputs accumulate via MessagesState. Inspect the first and second Alice snapshots and predict their message counts before running.

The live path instead creates a genuine catalog agent with the same checkpointer pattern:

config = {"configurable": {"thread_id": "alice-shopping"}, "recursion_limit": 8}
# Pass config on BOTH turns, and SessionContext("alice") on every invocation.

Alice states a temporary 3000-cent budget, then asks whether two notebooks fit it. Inspect the complete checkpoint messages, not only the last reply. The numerical total comes from the catalog tool; recall of the earlier budget comes from supplied history. Both sources are necessary for the comparison.

Guided completion and diagnosis

Guided completion: omit the stable thread configuration in a copy and predict which state cannot be found. Restore it on both turns. Independent variation: create another Alice thread and determine which facts should be absent; use the exercise.

If the agent forgets a budget, first inspect whether the earlier message exists in its checkpoint and selected context. Do not conclude that the model's weights “lost memory.” If it guesses a budget in Bob's conversation, distinguish an actual leaked checkpoint from unsupported inference.

Exit and review

Show retained messages and explain the application's role in recall. Demonstrate same-thread accumulation and new-thread isolation without pretending the offline graph generated text. Corrections: ordinary inference does not train weights; thread identifiers are lookup keys, not authentication. Review checkpoint durability in Module 10. See the API map. Focused follow-up: why can a graph reconstruction retain memory while process restart loses it?
