## Retrieve earlier concepts
What is a retry budget? Which side effects occur after approval? After attempting: physical retries differ from logical model invocations; local action recording belongs after the durable approval boundary.

## Execution model
The server admits at most `--max-workers` connections (default four), including request handling. Excess receives 503 rather than spawning unbounded threads. Bodies are capped at 16 KiB, read timeouts are bounded, and workflow operations have a whole-request deadline. The server uses a spawned process for each operation, not a background thread left running after a 504. It terminates and joins that worker on deadline, shutdown, or detected client disconnect.

This is deliberately expensive process isolation for a small local course application, not a throughput recommendation. Workflow locking serializes database graph runs; concurrent HTTP admission does not imply parallel SQLite writes.

## Worked cancellation
Run `uv run python labs/14_production/main.py --check`. It sends an actual complete request and closes the socket. With a known `X-Request-ID`, `/requests/<id>` exposes owner-filtered transient outcome. Logs record cancellation or response disconnect. The lab then inspects persistent thread state.

**Important:** the worker may already have committed checkpoint or action data. Cancellation means the response/work process ended, not transactional rollback. Before retrying an approval, inspect the thread/action sink; rely on stable action identity rather than assuming no effect.

## Guided and independent practice
Predict whether a paused draft, approved action, and request-status record each survive restart. Supply a missing inspection step before retry. Use [the exercise](../../exercises/14_production.md) to change the deadline and inspect actual outcomes.

## Failure diagnosis and exit
502 exposes worker/upstream failure class without raw provider text; 504 exposes deadline expiry. Live lab mode also uses a real unreachable provider endpoint with genuine configuration. Provider SDK retries remain bounded by runtime settings; no extra service retry layer is hidden. Exit by showing cancellation evidence, persisted-state uncertainty, and a repair decision. Revisit those semantics during [rollback](04.md); [solutions](../../solutions/14_production.md) distinguish overload control from a per-user rate limiter.
