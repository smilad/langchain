14.1 — A served application has a configuration boundary

Mission/objective: advance the mission by starting a real localhost HTTP application and tracing authenticated requests into persisted review state.

Prerequisites: durable approval and code-level authorization. Check: distinguish thread identity from user authentication.

Sources/version: Python 3.14 HTTP server, LangGraph persistence, and interrupts, checked 2026-10-12. Installed baseline Python 3.14.0, LangGraph 1.2.14, SQLite checkpointer 3.1.1; verification records exercised behavior. Human-draft requests need no model; live generation requires explicit consent, configured model, and provider credentials.

Recall

Does a body field named user_id prove identity? What should readiness prove? After attempting: identity is derived from a validated bearer token; readiness checks local prerequisites, not universal downstream availability.

Mental model and flow

HTTP bearer → token-to-user mapping → validated route/body → owned workflow process → independent SQLite connections → persisted state → JSON response

The server binds only 127.0.0.1. COURSE_AUTH_TOKENS is a JSON map of tokens to supported identities, never printed. Request bodies cannot select identity. Each operation uses the workflow's ownership checks too, so routing alone is not the isolation boundary.

This uses the standard-library server to make local operations visible. Python explicitly warns that http.server is not recommended for production. There is no TLS, hardened reverse proxy, distributed identity, or internet-facing deployment guarantee here.

Worked request

Follow the runbook to configure tokens, then run uv run python -m langchain_learning.service --port 8765. GET /health reports process liveness. GET /ready checks existing SQLite files and shutdown state; it explicitly does not probe the provider.

POST /threads/start accepts thread_id, question, and either an explicit human draft or live:true. A human draft is never labeled generated output. Both paths pause before a local action. A successful response wraps the workflow result in result; inspect its status and pending review, not just HTTP 200.

Guided completion and transfer

Trace the missing arrow from token validation to workflow identity. Independently run Alice and Bob using the exercise, then try a body user_id. Predict rejection before sending it.

Diagnosis, exit, review

A 401 indicates missing/invalid bearer; 403 indicates an ownership/permission boundary; 400 identifies rejected fields or state. Do not fix these by granting broader prompt access. Exit with a real human-draft request and identity-isolation demonstration. Review with the capstone; API map documents the exact entrypoint and workflow interface.
