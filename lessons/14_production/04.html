14.4 — A runbook includes the way back

Mission/objective: meet the mission by operating the application outside an IDE, stopping it cleanly, and rehearsing a rollback that protects persistent state.

Prerequisites: persistent operations, lockfile reproducibility, and evaluation tradeoffs. Check: distinguish restoring an executable from restoring application data.

Sources/version: uv project environments, SQLite online backup, and Python server shutdown, checked 2026-10-12. Python 3.14.0 and repository lockfile; verification contains runtime evidence. Remote hosting is optional and not claimed hardened by this local server.

Retrieval warm-up

What does a lockfile reproduce? Can process rollback undo a committed action? After attempting: dependencies, not provider behavior or credentials; code rollback does not erase already recorded effects.

Deployment choice

The chosen mechanism is a locked local Python process, python -m langchain_learning.service. Bind is intentionally restricted to localhost. SIGINT/SIGTERM stops admission, signals active handlers, terminates workflow workers, joins them, closes the server, and emits a stopped event. Shutdown is initiated outside the serving loop to avoid shutdown() deadlock.

A real internet deployment would require a reviewed production server, TLS, identity lifecycle, proxy limits, observability/storage policy, and an operations owner. None is supplied by a successful localhost response.

Worked runbook

Use the lab README: uv sync --locked, configure token bindings and state paths, start the service, probe health/readiness, create a human draft, stop, restart, inspect, decide, and check /actions. Repeat with live consent only after the deterministic boundaries work. Measure latency and usage for the intended workload before choosing targets; the course invents no universal SLA.

Before changing code or state schema, stop all writers and back up both SQLite files with SQLite's backup API. Keep code revision and lockfile together. Start a last-known-good checkout on a different localhost port against copies of compatible backups; run readiness and inspect a pending thread before moving any traffic. Do not overwrite the working directory with a destructive Git reset. Do not restore only checkpoints while leaving a mismatched action sink.

Guided completion and independent failure

Supply the missing post-rollback inspection: verify the pending thread and owner-filtered action count. Use the exercise to rehearse rollback with an edited draft. Diagnose 503 readiness by checking storage/configuration before resetting data.

Exit and later review

Produce actual start/stop/restore evidence, a known-good revision, and a state-compatibility limitation. Preserve actions already committed; no external undo is implied. Revisit this runbook in Module 15 and compare your evidence with the solution, not with an imagined production guarantee.
