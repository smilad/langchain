# 14.3 — Persistent state is operational data

**Mission/objective:** advance [the mission](../../MISSION.md) by resuming approval after a real server restart and retaining useful, minimal failure evidence.

**Prerequisites:** [cancellation semantics](02.md), durable checkpoints, and idempotency. Check: explain why an in-memory request record is not durable workflow state.

**Sources/version:** [LangGraph durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution), [Python SQLite](https://docs.python.org/3.14/library/sqlite3.html), and [persistence](https://docs.langchain.com/oss/python/langgraph/persistence), checked 2026-10-12. Python 3.14.0, LangGraph 1.2.14, checkpointer 3.1.1; see [verification](../../docs/VERIFICATION.md). Local persistence is real, but no exactly-once external email claim is made.

## Recall
Why place the side effect after interrupt? Why bind an action ID to an owner? After an attempt: resumed execution can revisit nodes; stable identity prevents duplicate local recording and stops cross-user access.

## Three stores, three responsibilities
| Data | Lifetime | Purpose |
|---|---|---|
| SQLite checkpoints | Process restart | Graph state and pending review |
| SQLite action sink | Process restart | Real synthetic approved-action records |
| In-memory request outcomes | Current process, last 256 | Diagnose cancellation/failure |

Each request's child process enters its own `SupportWorkflow` context and closes SQLite connections before returning its result. The workflow's cross-process lock protects serialized graph execution. Do not share a checkpointer connection between arbitrary HTTP threads and simply hope SQLite tolerates it.

## Worked restart
The model-free [production lab](../../labs/14_production/main.py) starts two human-authored drafts simultaneously, denies Bob access to Alice's thread, stops the actual service subprocess, and restarts using the same files. Alice approves twice with the same decision; her sink must have one action. Bob rejects; his sink must be empty. These are deterministic workflow invariants, not evidence of generated draft quality.

Logs report event names, request IDs, status, elapsed time, and exception class. They omit bearer headers, prompts, drafts, document content, and raw provider exceptions. The returned workflow state still contains synthetic application data, so even authenticated responses need retention and access rules in a real deployment.

## Guided completion and variation
Predict which data remains after restart; supply the missing state-inspection request before approval. Independently edit rather than approve a draft using [the exercise](../../exercises/14_production.md). Diagnose duplicate actions by inspecting action identity and workflow replay, not by hiding the second row.

## Exit and review
Demonstrate restart, pending review, one approved action, and no rejected action. Explain what a schema change could invalidate: checkpoint serialization, ownership tables, and action uniqueness. There is no generic migration claim; a real schema change needs an explicit migration/backup/recovery design. Revisit state compatibility in [rollback](04.md), and consult [troubleshooting](../../reference/TROUBLESHOOTING.md) before deleting local state.
