15.4 — Teach the application and state its limits

Objective: write a reproducible tutorial and demonstrate transfer to a changed question or corpus constraint without hiding failures.

Prerequisites: the architecture, execution, evaluation, and production operations. Cite the exercised dependency versions from the verification report, not whichever release is newest when you publish.

Recall

Explain why a smooth demo can conceal a retrieval miss, an authorization defect, or a replayed side effect. Sketch the system from memory, then compare it with your actual source and observed trace. Correct the diagram if it describes intended rather than real behavior.

The tutorial is a consumer contract

A new learner must be able to start with a checkout rather than your IDE state. Include Python/uv prerequisites, the exact locked installation command, safe environment-variable configuration, the no-cost local path, and the explicit live path. Explain the TUNA package-mirror choice and how a user with accessible PyPI can deliberately re-resolve; changing the index is an environment change, not an invisible workaround.

Never include your .env, bearer tokens, provider credentials, private traces, or generated data copied from a real workplace. The course corpus and action sink are synthetic. Give a reader the question and expected behavior, not an exact model sentence that a stochastic system cannot guarantee.

Worked runbook outline

  1. Check interpreter, dependency versions, and external langchain import origin.
  2. Inspect authorized current passages for the selected question.
  3. Start a manual-draft workflow to learn durable approval without paying for a model.
  4. Start a live grounded draft only with consent; inspect evidence and review it explicitly.
  5. Stop/restart, resume the same owned thread, and observe the local action record.
  6. Run the evaluation protocol and read per-case failures.
  7. Serve the application locally with token-bound identities; exercise concurrent users and documented failure behavior.

Explain what cancellation guarantees: a disconnected client does not prove that a database operation was rolled back. Inspect persisted thread/action state before retrying. Similarly, the atomic unique local action record does not establish exactly-once delivery to an arbitrary external service.

Independent transfer

Choose the warranty policy rather than the return policy, or add a new synthetic public source with explicit ID/version metadata. Predict the ingestion/retrieval changes, rebuild the relevant index, and show the new evidence before generating an answer. Keep ownership, review, and action identity invariants unchanged.

Ask another learner to follow your tutorial. Record concrete points where setup or concepts were unclear; revise those explanations rather than adding a new abstraction. If no peer is available, rehearse from a clean environment and say that external learner feedback has not been collected.

For a failure investigation, remove a prerequisite from your runbook and identify the exact command that becomes unusable. Add the missing explanation with its diagnosis, not a vague “install everything” instruction.

Exit check: supply diagrams, reproducible commands, evidence-supported behavior, evaluation/limitations report, and an independently explained variation. A learning record is written only after the learner actually demonstrates the skill; no course-generation process can manufacture that evidence.

Review: revisit the architecture and changed-domain task after a delay. The purpose is retained reasoning, not memorized commands.

Sources: deployment concepts, release policy, the teaching rubric. Ask the assistant to review your explanation without rewriting it for you.
