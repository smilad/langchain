# 15.3 — Evaluate the baseline, then justify one improvement

**Objective:** produce a failure-aware comparison that separates retrieval quality, answer support, authorization, operational behavior, and cost.

**Prerequisites:** [evaluation](../08_evaluation/01.md) and [the capstone execution](02.md). See [the verification report](../../docs/VERIFICATION.md) for exercised versions and proof limits. Provider-dependent runs require explicit model/embedding configuration and consent; never publish a synthetic score as a generated-answer result.

## Retrieval warm-up

Why is a development-set improvement not evidence of held-out improvement? Which evaluator can detect a valid source ID attached to an unsupported claim? Answer before reading your earlier evaluation notes.

## Establish the comparison protocol

The course dataset has 20 stable cases: eight answerable, four unanswerable, four conflicting/outdated, and four adversarial/access-boundary cases. Twelve are development cases; eight are held out. This is an instructional benchmark, not a strong estimate of production reliability.

Run the deterministic development checks first:

```bash
uv run python labs/08_evaluation/main.py --check
```

With a live provider configured, establish and freeze the model/retrieval configuration on development cases:

```bash
uv run python labs/08_evaluation/main.py --live \
  --freeze-config .course/rag-config.json
uv run python labs/08_evaluation/main.py --live --split held_out \
  --config .course/rag-config.json --output .course/rag-heldout.json
```

Do not use the held-out answers to adjust the prompt, chunking, or model settings while calling that split independent. If you inspect failures and tune on them, they have become development evidence; a fresh holdout is needed for the next confirmatory comparison.

## Read per-case evidence

For an answerable return-policy question, inspect the retrieved current passage, the generated claim, and the cited ID. A correct ID is a structural check; a reviewer still needs to determine whether the period, start date, and eligibility conditions are supported.

For remote-work contradictions, assess whether the answer acknowledges incompatible current evidence. For a finance question, verify the access boundary before interpreting the answer. For malicious-source content, ask whether it influenced instructions or attempted unauthorized behavior. Do not average a security leak away because most ordinary questions passed.

## One-variable experiment

Use development cases to compare lexical retrieval with the semantic strategy, configuring the actual embedding model. Keep model, prompt, dataset, trial count, and other retrieval settings fixed. Record latency and reported token usage; estimated price requires named pricing assumptions. More relevant passages may improve support while extra model calls worsen latency/cost. Either outcome is useful.

For guided practice, classify one failed case as ingestion, retrieval, generation, evaluator, or environment failure. Then independently diagnose a different case. A provider outage is not a failed knowledge objective, but it leaves the live behavior unverified.

For a failure investigation, make a hypothetical grader award points for citation presence alone. Explain the plausible false positive and replace that criterion with actual claim-to-evidence support review.

**Exit check:** publish a per-case report, configuration/trial details, measured-versus-estimated costs, at least one diagnosed failure, and the limits of the benchmark. Reuse the rubric on an unfamiliar question later.
