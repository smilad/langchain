04.3 — Build a bounded create_agent loop

Objective and prerequisites

Serve the mission by constructing the simplest catalog agent and explaining its stopping boundary. Prerequisites: requested versus executed calls, validated outputs and message roles. Warm-up: who computes a quote? Is temperature zero a guarantee of termination? Attempt before reading the exit corrections.

Source/version: LangChain agents, consulted 2026-10-12. Verification records exercised Python 3.14/locked versions and bounded real quote-agent execution. --live needs privately configured tool-capable access, COURSE_ALLOW_LIVE=1, and a network-call budget. The local --check is not proof of model behavior.

Mental model

An agent is a model plus a harness. create_agent supplies the message-state loop and local tool execution. Our factory supplies only the real model, two catalog tools and a bounded-behavior instruction. It exposes no arbitrary calculator, browser, checkout or write capability.

from langchain_learning.catalog import build_catalog_agent
agent = build_catalog_agent()
result = agent.invoke(
    {"messages": [{"role": "user", "content": "Quote 2 notebooks."}]},
    config={"recursion_limit": 8},
)

The instruction says to stop rather than repeat a failed operation. This is useful guidance, but the code-level recursion limit is the backstop. It bounds graph supersteps, not tokens, exact dollars, elapsed wall-clock time or a fixed number of individual tool calls. Provider timeout and retries are separate controls in the shared runtime. Multiple calls can occur in one tools step.

The normal path is model request → tools → model response with no more calls. A missing-item result may also lead directly to a final explanation. A repeated loop reaches GraphRecursionError; no grounded final answer should be invented after that failure.

Worked bounded case

The lab uses limit eight for normal, missing and invalid requests. Its bounded case uses limit one on a real prompt requesting tool work, prints partial updates and reports either observed budget exhaustion or observed termination. It does not assume a model will choose the same plan on every trial. The outputs are not pre-recorded success claims.

Guided completion: before running, sketch a plausible two-step tool sequence and identify where one superstep is insufficient. Then annotate the actual trace. Independent variation: ask for two different items at limit three, predict whether the provider may issue parallel tool calls, and compare the actual run with the exercise.

Failure diagnosis and exit

Distinguish a step-budget failure from schema rejection, insufficient stock and transport timeout. Raising a budget may permit additional progress; it does not repair bad arguments or missing catalog data. Do not silently retry an impossible request until it “looks successful.”

Exit: demonstrate one tool-using answer and one bounded execution, explaining what the bound guarantees and what it does not. Corrections: deterministic Python computes cents; low temperature does not guarantee termination or correctness. Review stopping policies in Modules 09 and 11. Reference: API map. Focused follow-up: why can a run obey its step bound yet exceed an unacceptable monetary budget?
