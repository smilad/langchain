# 04.4 — Inspect intermediate messages and classify failures

## Objective and prerequisites

Advance the [mission](../../MISSION.md) by producing an evidence-backed diagnosis of a catalog-agent failure. Prerequisite: [bounded loops](03.md). Warm-up: does `found=false` mean an exception? Can a final answer be factual when no matching tool result exists? Attempt before reading the review corrections.

**Sources/version:** [Agents: invocation and streaming](https://docs.langchain.com/oss/python/langchain/agents) and [messages](https://docs.langchain.com/oss/python/langchain/messages), consulted 2026-10-12. [Verification](../../docs/VERIFICATION.md) records Python 3.14 local checks and actual normal quote-agent node/tool messages. Additional cases remain separate evidence gates. Live traces require compatible private access, explicit consent, and approved charges; use only synthetic data.

## Mental model: evidence before repair

An agent trace is a sequence of state updates, not a collection of final prose. The lab's `stream_mode="updates"` prints actual node updates through the shared JSON emitter. An AI message may have empty text but meaningful `tool_calls`. A tool message carries returned content and the matching call ID. Neither should be discarded because it does not resemble a friendly sentence.

| Observation | Category | Next diagnostic step |
|---|---|---|
| Strict quantity rejected | Input/schema | Inspect arguments and error type |
| Valid ID absent | Domain unavailable | Confirm `found=false`; stop inventing |
| Quantity exceeds stock | Business constraint | Compare quantity to actual stock |
| Repeated requests, no finish | Control flow | Inspect partial trace and step bound |
| HTTP/auth/timeout failure | Environment/provider | Inspect safe error; never print key |
| Final total conflicts with tool | Unsupported generation | Map claim back to integer-cent result |

## Worked investigation

```text
uv run python labs/04_tools_agents/main.py --check
uv run python labs/04_tools_agents/main.py --live --case missing
```

These commands are implemented; the local schema/data path is exercised in [verification](../../docs/VERIFICATION.md). The live command tests how the real model handles a missing item and remains unverified without its prerequisites. Wording is variable; acceptance is evidence-grounded unavailability, not a particular sentence.

Make a three-column trace worksheet: model-requested arguments; actual returned fields; final claims. For every numerical claim, point to `unit_price_cents`, `quantity` and `total_cents`. If the final response includes tax, delivery or a purchase receipt, those claims are outside the tool contract even when the subtotal is correct.

## Complete and vary

Guided completion: leave the failure-category column blank for a negative quantity and an absent ID, then fill it from the inspected boundary. Independent variation: change only the prompt to ask for 4 desk lamps. Explain why quantity four passes the 1–20 schema but fails stock three. Use the [exercise](../../exercises/04_tools_agents.md), then compare reasoning with its separate solution.

Do not hide an unsupported answer by overwriting it with canned success text. Preserve failures and record which boundary held. Do not upload even these traces to hosted tooling without understanding consent and retention.

## Exit and review

Pass the Module 04 gate with successful lookup, unavailable item, invalid tool input and bounded run; identify requested versus executed operations. A missing live configuration is an unverified live gate, not learner failure or fake success. Corrections: unavailability is a valid result; a final assertion alone is not evidence. Review failure categories in Module 08, and context leakage in Module 05. Reference: [troubleshooting](../../reference/TROUBLESHOOTING.md). Focused follow-up: which layer should change when an answer invents shipping costs despite a correct quote tool?
