# 04.2 — Separate requested calls from executed calls

**In plain words:** The model only asks for a tool call; your code decides whether to run it and what comes back. "Not found" is a normal result, not an error, and a model saying it checked something is not proof that it did.

## Mental model and flow

The model does not open `data/catalog.json`. It proposes a named operation with structured arguments. LangChain resolves that name to a Python tool; the tool validates arguments and executes its function. Its result is returned as a tool message correlated with a call ID. Another model step can then interpret the result.

```text
HumanMessage → AIMessage.tool_calls → schema validation
             → lookup_item → validated catalog.json → ToolMessage
             → next model response
```

A proposed call that failed validation has not performed a successful catalog operation. A final sentence saying “I checked stock” is not evidence either. Inspect the intermediate messages and the actual tool result before evaluating that sentence.

## Worked example: unavailable is a useful result

```python
from langchain_learning.catalog import catalog_tools
lookup, quote = catalog_tools()
print(lookup.invoke({"item_id": "invisible-widget"}))
print(quote.invoke({"item_id": "invisible-widget", "quantity": 1}))
```

The implemented contract returns `found=false`; the quote additionally returns `quoted=false` and `reason="item_unavailable"`. These describe **absence in this fixture**, not worldwide product availability. The catalog is explicitly synthetic, but results come from genuine JSON reads—not fabricated function strings standing in for data access.

Found-but-sold-out is different. `sold-out` is an existing item with stock zero. Its lookup succeeds; its positive-quantity quote fails the stock check. Our tools do not reserve inventory, deduct stock or include tax/shipping. A successful quote is not a purchase confirmation.
