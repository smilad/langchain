04.2 — Separate requested calls from executed calls

Objective and prerequisites

Advance the mission by tracing a model's requested tool arguments to actual local data access. Prerequisite: tool schemas and Module 02 message roles. Warm-up: which message role carries a tool result? Can a model's proposed function call prove the function executed? Attempt first; corrections appear in the exit section.

Sources/version: Tools and model tool calling, consulted 2026-10-12. Python 3.14/locked integration and actual model-selected quoting are exercised in verification. Local tool invocation is offline; live requires privately configured tool-capable access, explicit consent, and provider budget.

Mental model and flow

The model does not open data/catalog.json. It proposes a named operation with structured arguments. LangChain resolves that name to a Python tool; the tool validates arguments and executes its function. Its result is returned as a tool message correlated with a call ID. Another model step can then interpret the result.

HumanMessage → AIMessage.tool_calls → schema validation
             → lookup_item → validated catalog.json → ToolMessage
             → next model response

A proposed call that failed validation has not performed a successful catalog operation. A final sentence saying “I checked stock” is not evidence either. Inspect the intermediate messages and the actual tool result before evaluating that sentence.

Worked example: unavailable is a useful result

from langchain_learning.catalog import catalog_tools
lookup, quote = catalog_tools()
print(lookup.invoke({"item_id": "invisible-widget"}))
print(quote.invoke({"item_id": "invisible-widget", "quantity": 1}))

The implemented contract returns found=false; the quote additionally returns quoted=false and reason="item_unavailable". These describe absence in this fixture, not worldwide product availability. The catalog is explicitly synthetic, but results come from genuine JSON reads—not fabricated function strings standing in for data access.

Found-but-sold-out is different. sold-out is an existing item with stock zero. Its lookup succeeds; its positive-quantity quote fails the stock check. Our tools do not reserve inventory, deduct stock or include tax/shipping. A successful quote is not a purchase confirmation.

Guided and independent work

Guided completion: annotate each event in the lab's --live --case normal output as request, execution result or interpretation. Supply the missing link between a call ID and its tool result. Independent variation: use sold-out rather than an absent item and explain why the result shapes differ; continue in the exercise.

Failure investigation: predict how an ID containing ../ fails. It is rejected by the identifier schema; the string is never used as a path. A valid-but-unknown ID follows the missing-item path instead. If the agent invents a substitute after a failed lookup, preserve the trace and classify this as unsupported generation—not a failed JSON parser.

Exit and delayed review

Show the supplied arguments, resolved function and returned data for one call, then justify an unavailable-item answer from evidence. Corrections: a ToolMessage carries the result; proposing a call proves neither execution nor success. Review these distinctions in Module 08 evaluation and Module 13 transport debugging. See the lab runbook and API map. Focused follow-up: what evidence would disprove the assistant's claim that it purchased an item?
