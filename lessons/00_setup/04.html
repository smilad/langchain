00.4 — Await changes scheduling, not truth

Mission/objective: Support the mission by distinguishing synchronous work from cooperative async execution and tracing an exception to its boundary. Prerequisites: 00.2 and 00.3; identify the exception raised when a Request has negative quantity.

Sources/version: asyncio tasks, tracebacks. Checked 2026-10-12; installed authoring snapshot Python 3.14.0/Pydantic 2.14.1. Actual execution evidence is in verification. No model call or credential.

Retrieval warm-up

What is the difference between an exception and an invalid return value? Which interpreter owns the imported library? Before checking answers, predict whether marking a function async automatically makes a blocking call safe.

Mental model

A synchronous call occupies the caller until it returns. Calling async def creates a coroutine; an event loop must drive it. await suspends that coroutine while the awaited work permits progress. It does not create a parallel CPU, turn every function into nonblocking I/O, or guarantee completion order.

The lab appends scheduling events around await asyncio.sleep(0) and gathers two coroutines. This is actual event-loop scheduling, not a mocked network response. Its boundary is two coroutine objects → event loop → ordered results + event log. gather returns results in input order, even when tasks interleave. The lab checks that B starts before A ends; explain why the explicit yielding point permits this.

Worked example and fading

async def cooperative_work(name, events):
    events.append(f"{name}:start")
    await asyncio.sleep(0)
    events.append(f"{name}:end")
    return name

Run the setup check and inspect scheduling_events. As a guided variation, remove the scheduling point in a separate copy and predict the changed interleaving before execution. Then explain where a synchronous SDK or time.sleep would block the loop. A CPU-heavy JSON transform remains work on the event-loop thread unless explicitly offloaded; async syntax alone changes none of that.

Failure investigation

The same lab catches a deliberately invalid Request and extracts traceback frame names and line numbers. Start with the final validation rule, then follow main → read_request. A traceback's final exception is usually more informative than its first frame. Never respond to every traceback by reinstalling dependencies. Deliberately catching the diagnostic is not suppressing a real production failure: the case is named and asserted as invalid.
