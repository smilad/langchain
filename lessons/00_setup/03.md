## Mental model and worked example
A request is a proposed operation; validation decides whether the application accepts its inputs. A response describes what happened, not what the caller hoped would happen. HTTP carries these values across a network boundary, while Pydantic enforces a local Python contract.

The [setup lab](../../labs/00_setup/main.py) uses:
```python
class Request(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    request_id: str = Field(min_length=1)
    quantity: int = Field(ge=1, le=20)
```
A model validator separately rejects whitespace-only identifiers. `min_length=1` alone permits one space. `extra="forbid"` catches misspelled keys rather than discarding them. Strict integer validation makes the contract explicit: a JSON string `"2"` is not quantity 2. These choices are policy decisions, not universal defaults.

The flow is `HTTP/JSON bytes → decode → validate → operation → response`. This lab exercises decode/validate only; it is not evidence of an HTTP exchange. Interpret the printed error `location` as the failed field path and `type` as the validation rule. We avoid echoing full invalid inputs in general error reports because real inputs might be private.

## Guided task and transport diagnosis
Add a maximum length for an identifier in your own variation, predict its error, then execute it. Explain why your validation must happen before an operation, not after it has already charged someone.

Now classify three hypothetical failures: no response before a deadline; HTTP 429; completed HTTP response containing a wrong business answer. The first is a timeout, the second a rate/quota boundary, the third an application/model correctness problem. A timeout does not prove the server did nothing; a 429 is not evidence of malformed JSON.
