# 02.3 — Render inputs explicitly before calling the model

**In plain words:** A prompt template fills named slots to produce messages. You will render one locally, without a model, so you can see exactly what would be sent and catch a missing variable early.

**Mission/objective:** Advance the [mission](../../MISSION.md) by rendering a prompt and inspecting the separation between instructions and user data. Prerequisite: [02.2](02.md); distinguish a human message from a tool result.

## Mental model and flow
A template is a deterministic mapping from named values to a prompt value. It is not a model response. In this lab, a fixed system instruction defines the classifier and a human placeholder contains the learner's text. We inspect this intermediate representation before transport so missing variables cannot masquerade as model errors.

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", instructions), ("human", "{text}"),
])
rendered = prompt.invoke({"text": "I was charged twice."})
messages = rendered.to_messages()
```
The boundary is `dict[str, str] → ChatPromptValue → list[BaseMessage] → model`. `invoke` on a template renders; `invoke` on a model sends a request. Same interface name, different component responsibility. Naming every stage prevents accidental paid calls while debugging.

## Worked example and fading
Run the [check](../../labs/02_models_messages/main.py). It passes a user string containing literal braces `{quantity}` and an instruction-like phrase. Values inserted into the `{text}` slot are not recursively formatted as template syntax, so those braces remain user data. This prevents a formatting error, not prompt injection.
