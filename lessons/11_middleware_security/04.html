11.4 — Security evidence must name its scope and version

In plain words: A security report names what was enforced in code, what the model did, and what was not tested. One clean run does not prove safety against all prompt injections.

Mission. Objective: produce an adversarial report that distinguishes enforced ownership from observed model behavior and redaction limits.

Prerequisites and retrieval

The prior three lessons and Module 08 per-case evaluation. What does a denied tool message prove? What if the model never called the tool? Can a public identity string authenticate an HTTP request? Attempt answers before writing your report.

Source and compatibility

Guardrails, runtime, and custom middleware, checked 2026-10-12. Installed baseline: Python 3.14.0, LangChain 1.4.4, LangGraph 1.2.14, langchain-openai 1.7.0; lockfile. Verification distinguishes exercised local commands from unavailable live proof;

Mental model

Authorization, minimization, redaction and human review solve different problems. Authorization decides who may perform an operation. Minimization reduces data entering context. Redaction changes visible text but may miss encoded or paraphrased content and cannot retract upstream disclosure. Human review accepts or edits a specific proposal, not every future operation from that thread.

The local CLI deliberately accepts a trusted demo identity. The HTTP service in Module 14 authenticates tokens before supplying workflow identity. The model's requested user_id is not accepted by the inspection tool; the schema forbids extra fields and trusted runtime context owns identity. An attacker knowing a thread ID gains no inspection/resumption permission.

Worked report structure

Run the lab. For every attack record input/source ID, trusted actor, requested capability, actual execution outcome, action count and interpretation. Record interpreter/package lock, model ID when used, prompt revision, declared trial count and whether any external tracing was enabled. Never paste tokens or full configuration objects.

The check mode establishes actual local permission/schema/sink boundaries, not middleware traversal through a model. Live mode observes real middleware integration and provider variability. A successful check plus one clean live output is still not proof against all prompt injections. The unsafe fixture's synthetic leak is a counterexample to text-based permission, not measured model leakage.

Guided diagnosis and independent gate

If an output contains a synthetic secret, locate how it entered the outbound context; deleting it from the final display alone is not a complete fix. If an unauthorized action commits, inspect the execution boundary and persisted human decision. Use the exercise to test altered arguments and a fresh attack, then state residual semantic risks explicitly.

Exit and review

Explain code-level ownership, demonstrate zero unauthorized effects, distinguish model attempts/refusals from enforced denials, and publish versioned limits. Revisit the report in the Module 15 capstone with held-out adversarial cases. Solutions.
