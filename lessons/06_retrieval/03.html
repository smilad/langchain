Mental model

Lexical retrieval here creates term-frequency vectors weighted by inverse document frequency, then ranks by cosine similarity. Common stopwords are discarded and zero-overlap queries return no documents. This is deterministic search over words, not an embedding model and not a semantic simulation. An exact order identifier such as SHIP-42 is a useful lexical test; a meal question phrased as getting money back for dinner may expose its vocabulary limits.

Semantic search uses the real OpenAIEmbeddings integration and LangChain InMemoryVectorStore. The configured COURSE_EMBEDDING_MODEL determines the vector space. Authorized current document texts are embedded when that identity's in-memory store is built; a query is separately embedded on every search. Both are remote, potentially paid requests. The code requires live consent, a key, and an explicit embedding model; it never falls back to fake vectors or lexical output while calling it semantic.

A vector store stores vectors and text/metadata. A retriever is an interface returning Documents for a query. Our lexical PolicyRetriever subclasses BaseRetriever, while semantic stores use as_retriever(search_kwargs={"k": k}). Both expose invoke, making the generation boundary independent of the ranking mechanism. Similarity is not truth, authorization, or a guarantee of relevance: semantic top-k normally returns something even for an unrelated query. Read the text before answering. Changing the embedding model selects a fresh store, and changed sources invalidate cached stores.

Data/control flow

Authorized text → real document embeddings → vector store; query → real query embedding → retriever → Documents

Worked example

Run from the repository root after uv sync --locked. This is implemented code/command guidance, not an observed output:

from langchain_learning.retrieval import PolicyIndex
# No remote requests in this baseline:
print(PolicyIndex().as_retriever("alice", k=3).invoke("SHIP-42"))
