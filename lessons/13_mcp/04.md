# 13.4 — Unavailable is not the same as disconnected

**Mission/objective:** support [the mission](../../MISSION.md) by observing unavailable-server and disconnected-client failures, releasing real resources, and classifying errors before attempting recovery.

**Prerequisites:** [capability boundaries](03.md), async context managers, and timeouts. Check: distinguish a domain unavailable-item result from a failed transport connection.

**Sources/version:** [LangChain connection lifecycle](https://docs.langchain.com/oss/python/langchain/mcp/connections), [MCP tool errors](https://docs.langchain.com/oss/python/langchain/mcp/tools#errors), and [FastMCP Client](https://gofastmcp.com/clients/client), checked 2026-10-12. Python 3.14.0, LangChain 1.4.4, FastMCP 4.1.0. Adapter APIs are beta; [verification](../../docs/VERIFICATION.md) records actual runs rather than borrowing documentation outputs.

## Recall
Can a model repair a broken TCP socket? Does exiting adapter discovery make every adapted tool permanently unusable? After an attempt: transport repair belongs to the client/application; adapted tools can reconnect because they hold a reentrant client.

## Failure taxonomy
| Failure | Visible boundary | Decision |
|---|---|---|
| Missing catalog item | Successful structured domain result | Report unavailable |
| Invalid quantity | Error ToolMessage | Explain/correct bounded input |
| No listening server | Transport exception | Stop this integration attempt |
| Direct client used after context exit | Lifecycle exception | Re-enter an intentional context |
| Changed advertised schema | Discovery/argument mismatch | Review capability contract |

The lab does not retry a new server or silently fall back to direct Python. Such a fallback would hide the fact that the required integration never worked.

## Worked lifecycle
Run:

```sh
uv run python labs/13_mcp/main.py --check --scenario unavailable
uv run python labs/13_mcp/main.py --check --scenario disconnect
```

The first attempts a real localhost HTTP MCP connection at port 1, bounded by five seconds. It records the actual exception class. The second starts the real stdio server with `fastmcp.Client`, performs a real lookup, exits the context, verifies disconnection, and attempts another direct call. Using the direct client here intentionally distinguishes released transport from the adapter tool's reconnect behavior. Normal mode uses MCPAdapter, not an in-memory server.

## Guided completion and independent variation
Predict which context owns the subprocess before running either case. Supply the explanation for why an invalid-tool error reaches a model while a transport exception stops execution. Use [the exercise](../../exercises/13_mcp.md) to reconnect explicitly and inspect the refreshed capability catalog.

## Exit and review
Show the real before-disconnect result, disconnected status, and sanitized error category. Observe clean context exit; do not claim that it proves arbitrary remote infrastructure shuts down. Revisit lifecycle handling in [HTTP cancellation](../14_production/02.md) and consult [troubleshooting](../../reference/TROUBLESHOOTING.md) for interpreter/path failures.
