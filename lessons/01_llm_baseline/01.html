01.1 — A model call is not your application's memory

Mission/objective: Advance the mission by tracing text through a model call and identifying where state actually lives. Prerequisite: Module 00; explain a request/response and a timeout before any paid call.

Recall before explanation

Can a configuration-presence check prove authentication? Which parts of JSON validation are deterministic? Attempt answers before corrections.

Mental model and flow

A tokenizer represents text as tokens, which are not always words. A model receives a bounded context and generates output tokens. The context window limits what fits; output budgets limit generation, and some models count internal reasoning against that budget. Neither limit establishes factual accuracy. Character counts in this lab bound application input, not exact token cost.

Layer State it owns
Python application text, instructions, configuration, stored history
Request selected model + supplied context + output budget
Provider response generated content, completion status, reported usage
Model parameters learned weights, not this script's mutable dictionary

The baseline lab sends a single independent request. It does not pass a previous-response ID, attach a database or maintain conversation history. Calling it twice is not a demonstrated remembered conversation. Providers may retain data under their policies; that is a different issue from application context and must be reviewed before sending private content.

Failure investigation and variation

Predict what happens when a very long input exceeds the lab's 4000-character limit versus when a smaller input exceeds the provider's token context limit. The former is rejected before transport; the latter depends on tokenizer/model capability. Do not claim character count measures tokens. Attempt state/context task 1 in the exercise.
