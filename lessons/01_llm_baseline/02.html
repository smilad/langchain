01.2 — Instructions define a rubric, not a guarantee

In plain words: Instructions tell the model what you want, but your code must still check the answer. Here the only valid replies are billing, technical and other; anything else is rejected, and even a valid label can be wrong.

Mission/objective: Serve the mission by writing a classification contract and separating label validity from meaning. Prerequisite: 01.1; describe what a context window limits.

Sources/version: OpenAI text generation, model capabilities. Checked 2026-10-12; installed authoring snapshot Python 3.14.0/OpenAI SDK 3.29.0; exact resolution is in uv.lock. Verification records the author's live classification run. No paid request is needed for contract checks; observed label membership is not a general semantic-accuracy score.

Retrieve first

Where is a user's text stored before the call? Can three permitted strings still include a wrong answer? Try before opening feedback.

Mental model

Instructions tell a model what to attempt. Application validation decides what a downstream consumer accepts. The rubric here is billing for invoices/payments/refunds, technical for software errors/access, and other otherwise. User text is data, not a new classification policy. Separating instructions from input makes the boundary visible; it does not make prompt injection impossible.

The lab uses one permitted lowercase label, no punctuation or explanation. validate_label strips surrounding whitespace then checks exact membership. Billing, a paragraph and a JSON object are deliberately rejected. That parser does not classify the original complaint: accepting technical for a double charge would still be semantically wrong.

Worked example and fading

label = text.strip()
if label not in {"billing", "technical", "other"}:
    raise ValueError("invalid classification label")

Run --check; its strings are authored parser fixtures, not invented model answers. Identify the exact contract violated by billing because payment. Then complete your own missing membership check before a caller stores the value. Do not make the consumer accept explanations just to hide a model formatting defect.

Sampling parameters influence output distribution; low temperature is not a proof of correctness or repeatability. Providers and model families differ in accepted sampling controls. The direct Responses example deliberately omits temperature for broader capability compatibility. The later LangChain runtime uses temperature zero and therefore requires a model that accepts it. Never silently remove unsupported parameters and label that as identical behavior.

Failure investigation and independent variation

Predict the result for ambiguous input “My payment page crashes.” Specify a policy for overlapping categories before comparing live output. A completed but wrong label suggests rubric/prompt/model investigation; a timeout or 429 suggests transport/quota investigation. Attempt a changed-rubric exercise in independent tasks, then consult the solution.
