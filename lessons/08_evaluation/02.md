# 08.2 — Design and freeze an evaluation dataset

**In plain words:** An evaluation set needs fixed cases, a split between development and held-out, and a frozen configuration. Tuning against the held-out cases makes the result meaningless.

## Objective and prerequisites
[course mission](../../MISSION.md): Validate the exact case distribution and keep held-out examples outside development tuning.

Prerequisite check: Lesson 01; distinguish question, expected evidence and answer rubric.

## Recall before reading
Does an expected source ID specify an exact answer? Why does repeated held-out feedback invalidate a comparison? Attempt both questions before consulting the mental model; compare your reasoning afterward rather than copying definitions.

## Mental model
data/evaluations/rag.jsonl contains exactly twenty synthetic cases with stable IDs. Eight are answerable, four unanswerable, four conflicting/outdated, and four adversarial/access cases. Twelve are development and eight held_out. The development allocation is 5/2/2/3 across those categories, and the held-out allocation is 3/2/2/1; each category appears in both sets without pretending tiny counts are statistically balanced. Dataset bytes are pinned by SHA-256 in evaluation.py, preventing accidental edits to the benchmark during tuning.

Each case carries user identity, question, expected_source_ids, expected_abstained and a semantic_rubric. Source IDs describe evidence that should be retrieved, not pre-generated model answers. Empty expected evidence does not prove retrieved passages are irrelevant; unanswerable personal-detail questions may retrieve a general policy and still require abstention. Conflict cases expect both active notices so a reviewer can detect disagreement. Old revisions stay in ingestion history but must not become retrieval candidates.

Develop a retrieval change using only dev cases. --freeze-config exclusively creates an experiment record including strategy, k, trial count, model, embedding model, corpus and dataset fingerprints. A held-out run requires --config and exact settings matching that frozen record. For a comparison, register both strategies beforehand. The evaluator generates reports but does not modify prompts, tune thresholds, or regenerate answers in response to grades.

This is a teaching split, not access-controlled secret benchmark storage; learners can technically open the file. The methodological obligation is to avoid inspecting held-out outcomes while choosing a design. After final review, write down limitations and regressions. If the corpus changes, do not silently reuse the same benchmark/config as if it measured the same system.

## Data/control flow
`Development questions → one chosen configuration → frozen record → held-out single review → per-case report`

## Worked example
Run from the repository root after `uv sync --locked`.

```sh
# Freeze on development (deterministic demonstration):
uv run python labs/08_evaluation/main.py --check --freeze-config .course/dev-config.json
uv run python labs/08_evaluation/main.py --check --split held_out \
  --config .course/dev-config.json --output .course/retrieval-heldout.json
```
