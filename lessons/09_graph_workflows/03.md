# 09.3 — Reducers define how partial updates become state

**In plain words:** A reducer says how updates to the same field are combined. Without one, two parallel steps that write the same field cause an error. A list with an add reducer appends, and returning an empty list does not reset it.

[Mission](../../MISSION.md). **Objective:** predict accumulated events and repair a real parallel-write conflict.

## Mental model
Each channel has its own update rule. Without an explicit reducer, a normal sequential update replaces its value. `Annotated[list[str], operator.add]` instead combines the old list with the new list. The reducer receives old accumulated state as the left argument and the node's partial update as the right argument.

For the lab's events channel, classify returns one classification event. Retrieve returns one retrieval event; constraints returns one constraint event. The draft adds another event. No node should return the complete accumulated event list: doing so would append prior events again.

## Worked example
Inspect `RequestState.events` in [the lab](../../labs/09_graph_workflows/main.py):

```python
from operator import add
from typing import Annotated
# Within the state schema:
# events: Annotated[list[str], add]
```

Run `uv run python labs/09_graph_workflows/main.py --check`. The check requires both parallel contributions to survive. It then compiles an equivalent graph with plain `events: list[str]`; supported execution must raise `InvalidUpdateError` because concurrent writes have no merge rule. These are actual graph executions, not a simulated exception or import check.

Order within concurrent branches is not a substitute for semantic correctness. Assert that both contributions exist; do not infer business priority from which appeared first. Addition is associative, but list concatenation is not commutative. If ordering matters, use explicit sequencing or normalize records by stable identity after merging.
